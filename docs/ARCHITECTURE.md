# Архитектура · предложение

**Согласования с поздней правкой 08.10, P-027:** актуальные требования — SPEC / DECISIONS. Первая постоянная комната базовая, без ключа для первого и всех следующих гостей после серверной проверки Telegram-сессии и блокировки; прежний общий ключ P-019 для неё заменён. Другие комнаты — с ключами, объём их реализации в MVP ещё не выбран. Независимая передача конкретной паре, Telegram-бот с уведомлениями, фото и блокировка доступа сохраняются. Бумажные мероприятия не интегрируем; сохранение `dating_*`/архива не объединяет режимы/лайки. Конкретная дельта схемы требует чтения действующего кода. Старые варианты ниже не переопределяют поздние требования; код пока не приведён к ним.

## Границы

Telegram → статический интерфейс Mini App по HTTPS → API → адаптер существующей базы `dating_*`. Тонкий бот принимает /start и отправляет уведомления через отдельный outbox-воркер. Операторский путь baza сохраняется.

До получения кода действующего сервиса здесь не создаём конкурирующую копию датамодели. Предпочтительно добавить маршруты к Python/Flask-модулю 5035 или выделить совместимый адаптер; окончательное размещение — после проверки nginx/auth и процессов. Порт 5032 и таблицы mx_* отменены прежними решениями.

## Авторизация и сессия

Клиент передаёт raw `Telegram.WebApp.initData`. Сервер проверяет HMAC-SHA256 на токене бота, auth_date и формат пользователя; только затем создаёт короткую сессию. `initDataUnsafe`, query event_id и присланный user_id не являются основанием прав. После первичного входа запросы идут с серверной сессией; повторную привязку билета контролируем отдельно. Нужен rate limit, ограничение тела запросов и запрет логировать raw initData/токен.

Для базовой комнаты сервер применяет выбранный P-027 доступ всех пользователей без ключа; административная блокировка проверяется при каждом защищённом действии и не снимается первым/повторным входом. Отсутствие CRM-связи/билета не блокирует базовый вход; подтягивание контакта требует отдельного доказательства владельца. Чек-ин `enabled` остаётся правилом исторического операторского события. Автовход не включает участие после профиля и не даёт лайк/согласие на контакт. Предложения таблиц ниже ещё предстоит сверить с этим правилом и действующей схемой.

Предлагается same-origin HTTPS, HttpOnly Secure cookie, SameSite и серверная проверка Origin/CSRF для изменяющих запросов; совместимость cookie проверяем в Telegram iOS/Android до финального выбора. Истечение initData влияет на обмен, а не обрывает каждое голосование; при истечении сессии даём открыть приложение заново. Админские права отдельные, не из поля клиента.

Реализованный `telegram_auth.py` пока только проверяет initData. Это не законченная авторизация: сессии, привязка билетов, права, rate limit и webhook ещё предстоят.

## Предлагаемые расширения модели (не миграции)

- `dating_bot_users`: валидированный Telegram ID, разрешение/факт доступности уведомлений. Возможность писать может изменяться; blocked отражаем по ответу API.
- `dating_participant_accounts`: связь Telegram ID с участником события, proof_method, verified_at, reviewed_by; уникальный владелец участника. Поддержка смены аккаунта только с аудитом.
- `dating_profiles`/`dating_profile_media`: профиль и фото, определение постоянного профиля или снимка зависит от Q07.
- `dating_participation_consents`: включение участия и версия согласия на показ/раскрытие контакта.
- `dating_app_event_policy`: окно голосования отдельно от жизненного цикла операторского события; взаимности появляются сразу.
- `dating_pair_episodes`: эпизод взаимности, время начала/окончания, ревизия; создаётся при втором лайке, позволяет не оживлять согласие от старой пары.
- `dating_contact_grants`: отдельное явное согласие владельца контакта получателю, эпизод пары, версия контакта и текста, granted_at/revoked_at. Детализация Q03a.
- `dating_deliveries`: outbox, попытки, отложенный повтор, lease, ошибка, message_id.
- `dating_app_audit`: административные изменения без избыточного копирования личных данных.

Названия и состав предварительные. Сначала снимок действующей схемы, затем дельта-миграция с откатом и проверкой архива. Не применять `docs/sources/ddl_v2_dating_delta.md` повторно как установочный скрипт.

## Лайки и мгновенные взаимности

У существующего `dating_likes` PK — from/to, source — одиночное поле. Оно не хранит одновременно независимые лайки админа и гостя. Перед API определить Q10 и контракт записи: транзакции, версия набора и явное разрешение конфликта. Отправитель определяется привязкой сессии; никогда не берётся из JSON.

Подтверждены мгновенные мэтчи. Сервер сериализует изменения по канонической паре min/max ID, атомарно фиксирует взаимность и outbox. Одновременные лайки не должны потерять взаимность или продублировать уведомление. Закрытие окна синхронизируется с записью лайка. Старый VIEW остаётся для архива; отдельный эпизод пары хранит жизненный цикл и согласия. Контактная выдача проверяет текущую взаимность, активность участников, блокировки, владельца/получателя согласия, эпизод и версию контакта.

## Фото

Защищённое хранилище и только валидированные производные. Разделить оригинал/превью; лимиты байтов и пикселей; удаление метаданных. Подписанный URL выдаётся после проверки доступа, живёт недолго. Отзыв участия/жалоба меняет видимость. Сроки удаления уточняются; невозможность запретить скриншот не компенсировать ложным обещанием приватности.
